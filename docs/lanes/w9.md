## The defect

`client/src/pages/production/ClickupPipeline.jsx:4-8` on `3a10be7` held two literals: the launcher's host
and its admin access token, the second appended to the iframe src as `?access=…`. Vite compiles both into
`client/dist/assets/index-*.js`, which is served to anyone who loads the page — signed in or not. So the
token was public, and the host was a per-store functional URL in shared engine code (R5 / R15): on Sandbox
and Throwaway that page pointed at Mineblock's tool.

Measured before and after with one script, `scripts/w9-bundle-grep.sh` — the before run is against a clean
`git archive` of `3a10be7`, built with the same `npm run build`:

| needle | `3a10be7` src / dist | this branch src / dist |
|---|---|---|
| `mineblock-video-launcher` | 2 / 1 | 0 / 0 |
| `mb-bdabeb1589f7160234f33dfb6118ed57` | 1 / 1 | 0 / 0 |
| `/mb-[0-9a-f]{12,}/` | 1 / 1 | 0 / 0 |
| `/access=mb-/` | 1 / 1 | 0 / 0 |

## The fix

Two new store-config keys, read at request time (R7), never compiled into anything:

- `VIDEO_LAUNCHER_URL` — normalised to a bare origin; a path/query/fragment cannot retarget the call.
- `VIDEO_LAUNCHER_TOKEN` — **write-only** (R20): never in `snapshot()`, never in a response body, never in a
  log line, reported only as `token_set` / `configured`.

One new router, `server/src/routes/videoLauncher.js`, mounted at `/api/v1/video-launcher`, every route behind
`authenticate` + `requirePermission('brief-pipeline', 'access')` — the same permission the page's own
`PageGate` uses:

- `GET /status` → `{ configured, healthy, reason, missing }`. The **server** makes the health call.
- `GET /open/:target` with `:target` in a two-member allowlist, `app` and `health`, which are exactly the two
  upstream endpoints the page called on `3a10be7`. Anything else is `400 target_not_allowed`.

`VIDEO_LAUNCHER_URL` is re-validated through `endpointAllowed` (the same SSRF guard
`server/tests/money-path/ssrf-guard.mjs` covers) on **every** request, and outbound fetches use
`redirect: 'manual'` so a 302 upstream cannot walk a validated host to an unvalidated one.

## The one design decision, and why (DECISION MADE)

`open/app` answers **302** rather than proxying the launcher's document. This was read out of the launcher's
own source, not assumed:

- `mineblock-video-launcher/client/src/api/client.js` reads `?access=` from `window.location.search`, stores
  it in `localStorage` under `mb_access`, strips it from the address bar, and sends it as `X-Access-Token` on
  every `/api` call.
- `mineblock-video-launcher/server/src/server.js:85-86` resolves the role from that header or that query.

So the token has to reach a document served from the **launcher's own origin** — that is where its
localStorage lives and where its same-origin `/api/*` calls go. A proxied document would store the token on
the dashboard's origin and then fire `/api/*` at the dashboard. Proxying the whole tool is the
general-purpose proxy this slice is not allowed to build, and editing the launcher is out of lane.

**What that buys and what it does not.** The token is gone from the bundle, from every response body and from
every log line. It still travels in the `Location` header of a response only an authenticated operator
holding `brief-pipeline:access` can obtain — i.e. exactly the people the launcher already grants admin to.
The exposure moves from "anyone on the internet who fetches a `.js` file" to "the operators who already have
it". Closing the remaining gap needs a change on the launcher (a short-lived ticket), which is Ludo's tree.

## Not done here, deliberately

- **The token is NOT rotated.** The value that was in the bundle stays valid on `mineblock-video-launcher`
  until Ludo rotates it there. **This slice removes future exposure, not past exposure.** After rotation the
  new value goes in `VIDEO_LAUNCHER_TOKEN` on `mineblock-dashboard` only, and nowhere else.
- `mineblock-video-launcher` was **read** (its source, on disk at `/Users/ludo/mineblock-video-launcher`) and
  never **called** and never **edited**.
- No migration. Nothing in this lane needs one, so 136 is still free.
- `server/config/` has no `env-keys.json` or equivalent — checked; the three `env.*.example` files are the
  registry in this repo, and all three carry the keys now.
