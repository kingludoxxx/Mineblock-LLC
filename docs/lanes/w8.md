# W8a — a brand-new store wore another store's wordmark

## The defect, measured

`scripts/browser-check-sidebar-switcher.mjs`, fixture 8a, on the tree before this lane — a runtime brand
answering `logoWhite: null` (which is exactly what the provisioner creates: it sets `BRAND_NAME`,
`BRAND_SHORT_NAME`, `BRAND_EMAIL_DOMAIN` and no logo urls):

```
8a. no logo, switcher trigger: {"surface":"store-switcher-button","imgs":["/logo-white.png"], "wordmark":null, ...}
8b. no logo, collapsed:        {"imgs":["/logo-symbol-white.png"], ...}
8c. no logo, no hub:           {"surface":"brand-block","imgs":["/logo-white.png"], ...}
```

`/logo-white.png` and `/logo-symbol-white.png` are one particular store's own bundled images in
`client/public`. The chain: `GET /api/v1/brand` answers null per unset key (correct — the server invents no
brand default, that would itself be a store literal in engine code); `client/src/config/brand.js` `apply()`
falls back per field to `FALLBACK`; and `FALLBACK`'s defaults were `'Mineblock LLC'` / `'Mineblock'` /
`'/logo-white.png'` / `'/logo-symbol-white.png'` / `'/logo-black.svg'` / `'mineblock.com'`.

## What changed

1. **`client/src/config/brand.js`** — the build-time `FALLBACK` carries no store: `name`/`shortName`
   default to the neutral placeholder `'Store'` (exported as `NEUTRAL_NAME`), every logo defaults to
   **`null`**, `emailDomain` to the RFC 2606 reserved `example.com`. **Every `VITE_BRAND_*` read is
   untouched** — only the right-hand side of each `||` moved. `apply()` is now exported as `applyBrand()`
   so a test can drive the runtime path without an HTTP server; `load()` is still its only production caller
   and `GET /api/v1/brand`'s contract is unchanged (same six keys, still all null with no env).

2. **`client/src/hooks/useBrand.js`** (new) — the runtime brand as React state. `brand.js` exports LIVE
   BINDINGS, and a component that reads a binding directly shows whatever it held at its last render. That
   was invisible while the build-time default was a real image and stops being invisible the moment the
   default is "no image at all", so the components that paint the brand now subscribe.

3. **`client/src/components/layout/StoreSwitcher.jsx`** — `BrandMark` no longer assumes a store has an
   image. With a logo it renders the image exactly as before. With **no** logo it renders a neutral text
   wordmark: the small rounded initial square plus the store's own short name in the sidebar's own type,
   and **no `<img>` at all** (a null `src` is a request for the current page and paints a broken-image
   glyph). Collapsed, where there is no room for a name, the initial square alone. This is the one place the
   wordmark lives, so the switcher trigger and the R21 plain brand block answer identically (asserted).

4. **`client/src/pages/Login.jsx`** — the login page did `<img src={BRAND_LOGO_WHITE}>`. Same rule: the
   image when there is one, the store's name as a heading when there is not. The email placeholder now uses
   `brand.emailDomain` instead of guessing `you@<shortname>.co`.

5. **`client/src/pages/public/SupplierPublicSheet.jsx`** — same for `BRAND_LOGO_BLACK` in the printed
   header, plus the two `BRAND_SHORT_NAME` strings, all through `useBrand()`.

6. **`client/src/components/settings/WorkspaceTab.jsx`** — the Workspace tab's name field was the literal
   `'Mineblock LLC'`; it now shows the runtime brand's name. Its placeholder member list (this tab is not
   wired to the team API) and `ProfileTab` / `ops/APIRuns` example addresses moved from `@mineblock.io` to
   `@example.com`.

# W8b — the hub's JIT user met a red 403 on the store's own home page

## The defect, measured

Two independent causes, both proved red before the fix.

**Client:** `client/src/pages/Dashboard.jsx` called `api.get('/kpi-system/home-dashboard')` regardless of who
was looking, and `server/src/routes/kpiSystem.js:259` gates that whole router on
`requirePermission('kpi-system', 'access')`. `scripts/browser-check-home-permissions.mjs`, fixture B, before
the fix: `requests=1 gateCard=false red={"banner":true,…}`.

**Server:** migration 126 seeded `hub_role_map` against `seeds/seed_roles.js`
(`owner → 'Admin'`, `operator/editor → 'Manager'`). Those are the platform's ACCOUNT-administration roles;
the dashboard's pages are gated on the PAGE keys migration 031 seeds (`dashboard`, `brief-pipeline`, …) and
**neither `Admin` nor `Manager` carries a single page key**. So the operator the hub calls the OWNER of a
store arrived with a role that opens nothing in the sidebar. `server/tests/hub-sso/w8-jit-role.mjs` before
the fix: `J1: hub owner -> Team - Full Access … got ["Admin"]`.

## What changed

1. **`client/src/pages/Dashboard.jsx`** — the page takes `usePermissions()` and does not make the request it
   is not allowed to make. `gated` is a STATE, not an error: it is set from the user's own permissions
   before any request, **and** from a 403 the server answers (the server is the authority; the client's copy
   of a permission can be stale). While gated the KPI block, the Amazon row, the profitability panel, the
   break-even chart, the daily breakdown and the revenue chart are replaced by one quiet `KpiNoAccess` card,
   the Live pill and the date picker are hidden (they control nothing), and the 60 s poll does not run.
   **The retry banner is untouched and is still shown for a real failure** — fixture C proves it.
   `/kpi-system/home-dashboard` is the only permission-bound request this page makes (grepped).

2. **`server/migrations/133_hub_role_map_page_roles.sql`** (new, additive, idempotent, runs on an empty
   database) — re-points the map. Each `UPDATE` matches **only** the row that still holds migration 126's
   exact seeded value (so a store that already re-pointed a row by hand is left alone — migration 131's
   guard shape) and requires the target role NAME to exist (a dangling name is a 403 on every hop). A second
   run matches nothing. `order.json` += one entry at the end (117 entries).

3. **`server/src/routes/hubSso.js`** — the map lookup is now one function, `mappedRoleName()`, taken by both
   the JIT creation and the new divergence audit. Behaviour of the lookup is unchanged (exact hub role, else
   the `'*'` row, else refuse). New: when an EXISTING user's roles do not contain the role the map would have
   created, one `HUB_SSO_ROLE_UNCHANGED` audit row records `{mapped_role, held_roles}`. Nothing is changed by
   it. A user whose roles already match writes no row (negative control asserted) — a log that always fires
   says nothing.

## THE MAPPING, AND WHY

| hub role | dashboard role | why |
|---|---|---|
| `owner` | **Team - Full Access** | The store's full-access role as named in the roles table (migration 031, "Access to all dashboard pages", + `orders:access` from 086). It is the only seeded role that actually opens the dashboard's pages. |
| `admin` | **Team - Full Access** | A hub admin administers the STORE. The dashboard's own `Admin` role is the USER TABLE's administrator (users / departments / audit / settings) and opens no page — a different job, and the more dangerous one to hand out by SSO. |
| `operator` | **Team - Production** | The next one down in the existing set: dashboard + brief pipeline + brief agent + magic ads + statics. No revenue pages (asserted: no `orders`, no `kpi-system`). |
| `editor` | **Team - Production** | Same work, same tools. |
| `viewer` | **Viewer** | Read-only: asserted to carry no write action on any key. |
| `*` (anything else) | **Viewer** | **Fail closed.** An unknown hub role, and a ticket with no role at all, both land here (asserted). A hub role that spells a dashboard role name selects nothing — the map is the only door (asserted). |

**Idempotence / no silent downgrade.** An existing user is never re-roled, in either direction: the store's
own decision about an account outranks the hub's. A second hop changes nothing and creates nothing
(`HUB_SSO_JIT_CREATE` fires exactly once, asserted). A user whose roles were deliberately changed by the
store keeps them — and the divergence is now written to `audit_logs` so "why does my owner see nothing" has a
trail. **A user with ZERO roles is deliberately NOT topped up**: stripping roles is a plausible way a store
soft-disables somebody, and granting the mapped role there would be fail-OPEN.

**DECISION MADE — `kpi-system:access` is NOT granted to `Team - Full Access`, and no role's permissions are
touched by this lane.** `kpi-system` (the "CEO Office" / the home page's KPI block) is granted to **no role
but `SuperAdmin`** anywhere in this repo's migrations — checked: `grep -rn "kpi-system" server/migrations`
is empty. That reads as a deliberate restriction, not an oversight, so widening it would be a silent
privilege grant to every existing holder of that role on the two live dashboards. The consequence, stated
plainly: **a hub owner landing on a new store sees the home page with its KPI block replaced by the quiet
"not available for your role" card.** That is now a designed state instead of a red error. If the lead wants
owners to see the figures, it is one line, per store, on that store's database:

```sql
UPDATE roles SET permissions = permissions || '{"kpi-system":["access"]}'::jsonb
 WHERE name = 'Team - Full Access';
```

`docs/HUB-SSO.md` **does not exist on this tree** (checked), so the mapping is documented here and, in the
form that ships with the code, in the header of `server/migrations/133_hub_role_map_page_roles.sql`. Lane E's
`docs/lanes/lane-e.md` still describes migration 126's seed and was not edited (another lane's handoff file).

- `scripts/browser-check-home-permissions.mjs` (new, 18 checks, real headless Chromium, no network): four

  Dashboard in the REAL shell with the REAL `usePermissions` hook. The `perms=none` identity is exactly what
  migration 133 maps a hub owner onto.
