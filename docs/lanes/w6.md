## What this half adds

**Server**

1. `server/migrations/132_session_hub_stores.sql` — `sessions.hub_stores JSONB` (nullable). Additive,
   idempotent, runs on an empty database (proved: 116 migrations on a fresh DB, second run 0 pending).
2. `server/src/services/hubSession.js` — `sanitizeHubStores(claim)`: array, each entry exactly `{code, name}`
   with `code` matching `^[A-Z0-9]{2,4}$` and `name` a non-empty string of at most 80 characters, at most 50
   entries (the list is CUT at the cap, a malformed entry drops the WHOLE list). `issueSession` parks the
   result on the new session row; `loadHubSession(sid, userId)` replaces `hubSessionIsLive` as the one read
   (same query, now also returning the list, so revocation costs no extra query); `carryHubStores` moves the
   list onto the row a token rotation creates.
3. `server/src/routes/hubSso.js` — reads `payload.stores` off the SIGNED ticket and hands it to `issueSession`.
   A malformed list is ignored, never a refusal: losing a dropdown must not cost an operator a live store.
4. `server/src/middleware/auth.js` — for a hub-SSO token, `req.user.hubStores` comes from that session row.
   A local login gets `[]`.
5. `server/src/controllers/authController.js` (`refresh`) — carries `hub_stores` onto the rotated session row.
   Without this the dropdown vanished ~15 minutes after every hop, which is the same class of bug Lane H1 fixed
   for the `hub_sso` mark itself.
6. `server/src/config/storeConfig.js` — `hub()` = `{origin: HUB_ORIGIN|null, sso_enabled: HUB_SSO_ENABLED === '1'}`,
   read at request time (R7), in `snapshot()` (PL/MB snapshots regenerated).
   `server/src/routes/storeConfig.js` — the answer gains `switcher: {current, stores}`. `stores` comes from the
   SESSION (`req.user.hubStores`), never from the request: a client-supplied list changes nothing (asserted).

**Client**

7. `client/src/hooks/useStoreSwitcher.js` — one shared read of `GET /api/v1/store-config`, defensively parsed,
   plus `switchUrl` / `addStoreUrl` / `manageStoresUrl`. `enabled` is false unless there is a hub origin AND at
   least one store.
8. `client/src/components/layout/StoreSwitcher.jsx` — the sidebar's brand block. Same logo, same height, plus a
   `ChevronDown`; the popover lists every store (rounded initial mark, name, a gold check on the current one),
   a divider, `Add store` (→ `<hub>/#add-store`) and `Manage stores` (→ `<hub>/`). Rows are real links with
   `target="_top"` to `<hub>/switch/<code>?next=%2Fapp%2Fdashboard`. Keyboard: Enter/Space (native button),
   Escape closes, Arrow/Home/End walk the menu, click-outside closes. `aria-haspopup="menu"`,
   `aria-expanded`, `role="menu"`/`menuitem`, `aria-current` on the current store.
   **With no hub or an empty list it renders the old brand block and nothing else** (R21).
9. `client/src/components/layout/Sidebar.jsx` — the brand block is now `<StoreSwitcher collapsed={collapsed} />`.
   Collapsed sidebar: the symbol logo is the trigger, as before.

## Decisions

- **The list lives on the session row, not in the token.** Fifty stores is ~4 KB of claims, the whole browser
  cookie budget, and the access cookie is re-minted every 15 minutes. The session row is already re-read on
  every hub-SSO request (no grace period, Lane E's A4), so this costs nothing.
- **Fail soft on an old schema.** The write is wrapped (one warning, not a 500) and the read uses
  `to_jsonb(s.*)->'hub_stores'`, so code running against a database that has not had migration 132 still logs
  operators in instead of 401-ing every hub session. `preDeployCommand: npm run migrate` makes this rare, not
  impossible (a rollback re-opens it).
- **Code shape `^[A-Z0-9]{2,4}$`** is the dashboard's own `STORE_CODE` grammar (`server/migrations/run.js`).
  The hub's gate is wider (`^[A-Z0-9]{1,8}$`), so a hub store code outside 2-4 characters would make this
  dashboard drop the whole list (no switcher, no error). Every code the hub's wizard mints today is 2-4; if
  the lead wants the wider shape, it is one regex here.

## W6b refinements (2026-09-11, on top of the W6 commit)

The hub's claim entries are now `{code, name, role, can_hop}`. This half accepts them, serves them and
renders them the way Ludo's reference screenshot does.

**Server**

1. `server/src/services/hubSession.js` — `sanitizeHubStores` rewritten around a per-ENTRY
   `sanitizeHubStore()`. **This closes W6's deviation 6**: a bad entry is now SKIPPED and the rest of the list
   is kept, where W6 dropped the whole dropdown on one bad entry, silently. Also:
   - `role` — optional string, at most **24** characters, default `''`. It is a LABEL for a pill, never a
     permission: every gate is taken at the hub. The 24-character cap is load-bearing, and is the reason a
     credential can never reach a pill (proved by a negative control in the store-config suite).
   - `can_hop` — optional boolean, default `true` (a W6 ticket listed only hoppable stores, so `true` is the
     right reading of its silence).
   - The LIST's code grammar is now the HUB's `^[A-Z0-9]{1,8}$`, documented in the code comment: the hub is
     the authority on what a store code is, and this dashboard is only rendering the hub's answer. **This
     store's OWN `STORE_CODE` is unchanged and still 2-4 characters** — a different question. Under W6 the
     narrower rule here deleted any hub store outside 2-4 characters from the dropdown with no error.
   - A W6-shaped entry (`{code,name}`) is still accepted and gains the defaults. An unknown KEY still drops
     that entry (now only that entry) — a deliberate hold, flagged for the lead in PROOF-W6.md.
2. `server/src/middleware/auth.js` — `req.user.hubStores` is run through the same `sanitizeHubStores` on the
   way OUT, so a session row written by the W6 code reads back in the current shape instead of reaching the
   browser half-filled. Same pure function both directions, so read and write cannot disagree.
3. `server/src/routes/storeConfig.js` — comment only; the handler already forwards what `authenticate` put on
   `req.user`, which is now the four-field shape.

**Client**

4. `client/src/hooks/useStoreSwitcher.js` — the same widened code grammar, plus a defensive `role` (string,
   <= 24, else `''`) and `can_hop` (boolean, else `true`) per entry.
5. `client/src/components/layout/StoreSwitcher.jsx` — the dropdown, in the sidebar's existing classes and
   tokens, no new visual language:
   - each row is `[check slot] name ............ [role pill]`. The check slot is always rendered, so every
     name starts at the same x. The pill is `bg-bg-hover text-text-muted`, uppercased by CSS — the TEXT is
     the hub's own word, printed, not a vocabulary this dashboard knows.
   - a `can_hop:false` store renders as a **`<span>`, not a disabled `<a>`** — there is no href, so a click
     cannot navigate at all. `text-text-muted` + `opacity-45`, `aria-disabled="true"`, a **"not connected"**
     pill instead of the role pill, and `title="Single sign-on is not enabled for this store yet"`.
   - footer: a hairline, then **"New store"** (Plus icon) -> the hub's `#add-store` entry W6 wired, then a
     quieter **"Manage stores"** (`text-xs text-text-faint`).
   - wording: "store" everywhere; the word "workspace" appears in this file exactly once, in the comment that
     bans it (see the R15 grep in PROOF-W6.md).
   - **keyboard and collapsed behaviour are unchanged from W6.** A greyed row stays focusable (`tabIndex=-1`,
     `aria-disabled`), so the focus count is still `stores.length + 2` and the arrow walk is literally the W6
     walk — and a screen-reader user can still read the row and its title.
   - the TRIGGER is deliberately NOT changed (it is still the brand logo + chevron). Ludo's reference shows an
     initial-square + truncated name; that replaces the store's brand mark, which is a bigger call than the
     acceptance lines make, so it is left for the lead. Flagged in PROOF-W6.md.
