## Decisions

- **The list lives on the session row, not in the token.** Fifty stores is ~4 KB of claims, the whole browser
  cookie budget, and the access cookie is re-minted every 15 minutes. The session row is already re-read on
  every hub-SSO request (no grace period, Lane E's A4), so this costs nothing.
- **Fail soft on an old schema.** The write is wrapped (one warning, not a 500) and the read uses
  `to_jsonb(s.*)->'hub_stores'`, so code running against a database that has not had migration 132 still logs
  operators in instead of 401-ing every hub session. `preDeployCommand: npm run migrate` makes this rare, not
  impossible (a rollback re-opens it).
- **Code shape `^[A-Z0-9]{2,4}$`** is the dashboard's own `STORE_CODE` grammar (`server/migrations/run.js`).
  The hub's gate is wider (`^[A-Z0-9]{1,8}$`), so a hub store code outside 2-4 characters would make this
  dashboard drop the whole list (no switcher, no error). Every code the hub's wizard mints today is 2-4; if
  the lead wants the wider shape, it is one regex here.

## What changed in the dashboard

### P1-1 — forwarding compatibility: an unknown key is IGNORED, the entry is KEPT

`sanitizeHubStore` (`server/src/services/hubSession.js`) rejected any entry carrying a key outside
`{code,name,role,can_hop}`. Measured on the real function before the fix: an unknown key on ONE entry cost
that entry; an unknown key on **every** entry — which is exactly what the first hub release that adds a fifth
field looks like — returned `0` entries and **emptied every store's dropdown**, with no error, no log line and
no failing test on either side. The hub deploys FIRST by design (that is what C1 in
`server/tests/hub-sso/w6-switcher-claim.mjs` proves for the ticket); this makes it true for the LIST too.

It is not a weaker posture: the four known fields are each validated on their own whatever else the object
carries, and the object that leaves the function is BUILT from them, so nothing unknown can reach a browser.
Recovery from the old behaviour would have been a dashboard deploy per store.

### P2-2 — a store name is NORMALISED, not just length-checked

`cleanHubStoreName` strips U+200B-U+200F, U+202A-U+202E, U+2066-U+2069 and U+FEFF, collapses whitespace runs
and trims. An entry whose name is nothing but those characters has no name and is dropped. `role` gets the same
treatment. The dropdown is the one list an operator reads before choosing which LIVE store to enter, and
`Safe<U+202E>erots-live` renders as a different store.

### P2-1 — `hub.origin` is a BARE origin on both sides

- **Server** — `storeConfig.hub()` now returns `new URL(HUB_ORIGIN).origin`; unparseable or a non-http(s)
  scheme returns `null` with ONE warning (`warnOnce`), which is the same answer as "no hub configured", so the
  client renders its plain brand block and the store keeps working on its own login (R21).
- **Client** — `bareOrigin()` in `client/src/hooks/useStoreSwitcher.js` does the same, because the client must
  not depend on the server's half being deployed first.

Measured before the fix: `https://hub.example.test#x` produced
`https://hub.example.test#x/switch/MB?next=%2Fapp%2Fdashboard` — the hub ROOT — on every row, silently; and a
secret pasted into `HUB_ORIGIN` reached the browser verbatim for the same reason.

### P1-3 — the A6 scope guard is scoped, not global (LEAD DECISION, 2026-09-11)

`server/tests/store-code/a6-no-read-path.test.mjs` is lane C2's guard: its `FORBIDDEN`/`ALLOWED` lists are
written for the store-code lane, so every file a different lane legitimately touches under `server/src` or
`client/` is a violation by construction. On this branch it named all 13 of the sidebar switcher's files and
made `run-all` red on a branch with no defect in it — which under R24 blocks every lane that is not C2.

**Decision:** the FILE-SCOPE assertion runs only when `A6_ENFORCE=1` **or** the current branch name matches
`/store-code/`. Anywhere else it prints

```
SKIP A6 scope guard: not the store-code lane (set A6_ENFORCE=1 to force)
```

and passes. Nothing is deleted and nothing is weakened: the same assertion is one env var away on any tree,
and W6c re-proved that it still bites (it is still red on this branch with `A6_ENFORCE=1`). The file's SECOND
test — the migration runner's store-code + lock-timeout contract — is a statement about a FILE, not a diff, so
it is true on every branch and always runs.

**Consequence for CI:** the integration branch should set `A6_ENFORCE=1`, or the guard skips there too (a
branch named `hub/main` does not match `/store-code/`). That is a CI configuration line, not a code change,
and it is the lead's to place.
